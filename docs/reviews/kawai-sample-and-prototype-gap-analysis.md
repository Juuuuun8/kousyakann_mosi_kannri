# 河合塾帳票と既存試作のギャップ分析

## 1 目的

技術仕様書v1.0の7章と8章を基準に、河合塾・全統共通テスト模試の4ページ帳票と既存試作を照合し、Phase 1で失ってはならない情報、再利用できる実装、作り直す必要がある契約を明確にする。本書には実PDFの氏名、学校名、受験番号、得点等を記載しない。

## 2 確認対象

- 技術仕様書v1.0
- 4ページ構成の河合塾・全統共通テスト模試 個人成績表1件
- 既存試作の `src/parser.js`、`src/workbook.js`、`src/page_app.js`
- Python版 `python/kawai_to_excel.py`

## 3 帳票から取得可能な情報

| ページ | 区分 | 主な情報 | 分析上の用途 |
|---:|---|---|---|
| 1 | 帳票識別 | 提供元、年度、回次、模試名、ページ番号 | スキーム判定、時系列、重複防止 |
| 1 | 受験者属性 | 学校コード、学校名、学年、クラス、校内番号、氏名カナ、受験番号 | 本人照合、学校比較。直接識別子として厳格管理 |
| 1 | 科目成績 | 得点、配点、偏差値、学力レベル、全国平均・順位・人数、現役・高卒平均、校内偏差値・平均・順位・人数 | 個人評価、分布比較、校舎・学校分析 |
| 1 | 換算指標 | 共通テスト換算得点、私大評価用偏差値 | 志望校分析、指導面談 |
| 1 | 成績推移 | 過去回ごとの科目得点、偏差値、レベル | 伸び率、停滞、指導効果 |
| 2 | 分野別成績 | 科目、設問番号、内容、本人得点・配点、全国・校内・同学力帯平均、差、得点率差、一段階上判定者平均・差 | 強み弱み、単元別指導、群比較 |
| 2 | 帳票評価 | 最良・最低表示、レーダー相当値、講評文 | 面談表示、原帳票の意味保存 |
| 3 | 志望校 | 最大9志望、日程、大学、学部、学科・方式、募集人員、判定 | 志望校別・判定別比較 |
| 3 | 合格可能性 | 本人得点または偏差値、満点、ボーダー、順位・人数、平均、評価人数分布 | ボーダー差、同一志望集団比較 |
| 3 | 教科別評価 | 志望校ごとの教科偏差値・本人得点・大学配点等 | 目標校に対する教科寄与分析 |
| 4 | 解答明細 | 科目、大問、解答番号、正誤記号、実マーク | 設問正答率、誤答パターン、無解答分析 |
| 4 | 記号定義 | 正答、誤答、部分点、正誤表示不可、無解答、余分マーク | 生の記号と正規化値の対応 |

帳票に空欄があっても、「未受験」「科目未選択」「帳票に非掲載」「解析不能」は同じ意味ではない。Phase 1では欠損理由を区別する。

## 4 既存試作で再利用できる考え方

- PDF.jsで全ページの文字と座標をブラウザ内取得し、PDF本体を外部送信しない。
- ページごとに解析関数を分離している。
- 科目成績、分野別成績、志望校、解答明細を別配列へ正規化している。
- 複数PDFの読込、同一受験番号の検知、利用者向け警告表示がある。
- 科目比較、分野比較、マーク比較、志望校判定という分析の初期仮説がある。
- 数式注入を考慮すべき出力経路が識別できている。

既存試作は参考実装であり、正本仕様にはしない。固定座標・正規表現・受験番号上書き・Excel再読込を、そのまま本番データ契約へ持ち込まない。

## 5 既存試作の主な不足

| ID | 不足または危険 | 必須対応 |
|---|---|---|
| GAP-001 | detect、extract、validate、normalizeの境界と結果型が明示されていない | 4段階を独立契約にする |
| GAP-002 | 帳票スキームを固定ラベルと座標で暗黙判定している | Provider、ExamFamily、年度、回次、帳票版を証拠付きで判定する |
| GAP-003 | 受験番号を生徒の上書きキーとしている | 受験番号はExam単位の識別子とし、システムPersonIDと分離する |
| GAP-004 | 同一受験番号で後勝ち上書きとなり、誤結合を検知できない | 重複、訂正、別人衝突を別状態にする |
| GAP-005 | 成績推移を正本データとして保持していない | 帳票印字値を履歴payloadとして保存する |
| GAP-006 | 志望校の評価人数分布、日程、教科別詳細等が一部欠落する | 志望校ブロックを無損失で保存する |
| GAP-007 | 分野別の講評・表示記号等が一部欠落する | 生値と正規化値を併記する |
| GAP-008 | 空欄、未受験、非掲載、解析失敗を `null` に集約しやすい | MissingReasonを導入する |
| GAP-009 | 警告があっても他の項目を保存できる構造で、登録可否基準が弱い | 致命、要確認、情報の3段階と登録ゲートを定義する |
| GAP-010 | PDFページ欠落、重複、順序変更、混在の検証が弱い | ページ集合とReportIdentityを検証する |
| GAP-011 | ParserVersion、SchemaVersion、PayloadFormatVersionがない | 3種類の版を独立保存する |
| GAP-012 | Excelファイルをローカル正本として追加読込する | 本番正本はGoogle Sheetsに限定し、通常Excel出力は実装しない |
| GAP-013 | 実データに依存した回帰資産がない | 合成PDFと座標fixtureでゴールデンテストを作る |
| GAP-014 | 性能・セル数・GAS実行時間の測定がない | 行形式とJSON方式を同一合成データで比較する |

## 6 Phase 1への結論

1. 既存パーサの抽出ロジックは、項目位置と解析上の知見を移植するための資料として使う。
2. 帳票から取得できる値は、分析で直ちに使わない値も含め、正本payloadから復元できるようにする。
3. 頻繁に検索・集計するキーと科目成績は通常列へ置き、可変・高密度な解答明細、印字履歴、志望校詳細等は版管理JSONを候補とする。
4. フロントエンドの見た目を先に固定しない。分析カタログとデータ契約を確定した後、合成データによる画面プロトタイプを作る。
5. 会社承認前はGASへ接続せず、ローカルの合成データで契約・容量・可逆性・UIを検証する。
