# 仕様変更提案

## 運用

技術仕様書v1.0と、その後に承認された最上位制約が衝突する場合に使用する。承認前にコードへ反映せず、承認後は仕様書次版、トレーサビリティ、フェーズ計画、テストへ反映する。

## SPEC-CHANGE-001 ML用CSVの端末ダウンロード例外

| 項目 | 内容 |
|---|---|
| 状態 | 方針承認済み 仕様書改訂待ち |
| 対象 | 仕様書6.7 ML用CSV出力 |
| 原則 | 個人情報の永続保存先は職場PC Googleアカウント所有のGoogle Drive上のGoogle Sheetsに限定する |
| 承認済み例外 | ADMINが明示操作したML用CSVだけは、直接識別子を除外し、監査記録を残したうえで利用者端末へ保存できる |
| 権限 | ADMINのみ実行可能とし、INPUTには画面表示・API実行の両方を許可しない |
| 出力 | 対象期間・項目を指定し、ML_IDを付与し、固定列定義とExportSchemaVersionを含める |
| 非保存 | Cloudflare、GAS、Google DriveへCSVファイルを保存せず、レスポンスにもno-storeを指定する |
| ブラウザ | 一時Blobから利用者の明示操作で保存し、完了後にObject URLを破棄する |
| 安全策 | CSV数式注入を防止し、ダウンロード前に用途限定・保存・削除に関する警告を表示する |
| 監査 | 出力者、目的、対象期間、項目、件数、ExportSchemaVersion、実行日時をGoogle Sheetsへ記録する。CSV本文は記録しない |
| 残課題 | 保存期間、利用後削除、端末での取扱いをPhase 1で会社運用規程として確定する |

### 必須テスト

- ML出力に氏名・メール等が含まれない。
- INPUTによる画面操作と直接API呼出しの両方が拒否される。
- ADMINの明示操作なしにダウンロードが始まらない。
- Cloudflare、GAS、Google DriveへCSVファイルが残らない。
- HTTP応答がキャッシュされず、一時Object URLが破棄される。
- 先頭が `=`, `+`, `-`, `@` の値でCSV数式注入が成立しない。
- ExportSchemaVersionと固定列定義が一致する。
- 出力条件と件数が監査され、CSV本文は監査ログへ残らない。
- 警告表示と確認操作を経なければ出力されない。

## SPEC-CHANGE-002 OTP・セッションの短期保存先

| 項目 | 内容 |
|---|---|
| 状態 | 方針承認済み 仕様書改訂待ち |
| 対象 | 仕様書6.1、6.2、9.2のOTP・セッション短期ストア |
| 新しい制約 | 利用者と結び付く個人情報をGoogle Sheets以外へ保存しない |
| 問題 | CacheServiceへメール、UserID、OTP状態、セッション対応を置くと、Google Sheets以外の保存となる |
| 初期方針 | 非共有システム台帳内のOtpChallenges、Sessionsシートへ、有効期限付きで保存する |
| セキュリティ | OTPとセッションIDは平文保存せずハッシュ化し、失敗回数、期限、失効状態を保持する |
| CacheService | 利用者と結び付かないnonce等に限定する |
| 清掃 | 時間主導トリガーと各API呼出し時の遅延清掃で期限切れ行を削除する |
| 影響 | Sheetsアクセス回数と競合が増えるため、Phase 1以降で負荷試験する |

### 必須テスト

- CacheServiceにActor、Email、UserID、OTP、SessionID対応が保存されない。
- OTPとセッションIDが平文保存されない。
- 期限切れ、REVOKED、ログアウト後のセッションが拒否される。
- 同時更新時にLockServiceで競合を防ぐ。
- 清掃失敗が認証成功に化けない。

## SPEC-CHANGE-004 Google Sheetsセル内JSONの正本利用

| 項目 | 内容 |
|---|---|
| 状態 | 方針承認済み 詳細設計はPhase 1 |
| 対象 | 設問別正誤・マーク等の高密度かつ可変な成績データ |
| 目的 | 情報量を落とさず、模試・回次・帳票改訂への追従性を保ちながら、Sheetのセル数とAPI入出力を抑える |
| 採用条件 | 実データ相当の件数・項目数で行形式と比較し、情報損失なく軽量化できることを確認した場合に限る |
| 正本性 | 元データの全項目、意味、順序、型を保持し、決定的な変換で完全復元できること |
| 版管理 | PayloadFormatVersionを別列に持ち、ParserVersionから独立して移行できること |
| 整合性 | ReportID、科目、件数、payloadハッシュを通常列へ持ち、保存直後の再読込で検証すること |
| 上限対策 | セル上限へ近づく場合は複数行・複数チャンクへ分割し、切り捨て・要約を禁止すること |
| 障害時 | 欠落・重複・順序不正・ハッシュ不一致があるpayloadは全体を無効化し、分析やML出力に使用しないこと |
| 検索性 | 校舎、年度、模試種別、回次、学校、志望校、科目、主要得点等の検索・集計キーは通常列または集計シートに保持すること |
| ML連携 | 設問単位の固定スキーマへ可逆的に展開し、ExportSchemaVersion付きCSVを生成できること |

JSON化は必須ではない。Phase 1で通常行形式、科目単位JSON、チャンクJSONを比較し、セル数、読書き時間、同時更新、復元時間、障害範囲、分析クエリの扱いやすさを測定して決定する。

### 必須テスト

- 正規化済み入力を保存・再読込・復元した結果が、型と順序を含めて元入力と完全一致する。
- 同じ入力から同じシリアライズ結果とハッシュが生成される。
- 最大想定件数とセル上限境界で切り捨てが起きない。
- チャンク欠落、重複、順序入替、改ざんを検出し、payload全体を拒否する。
- 旧PayloadFormatVersionを読み出すか、監査可能な手順で新形式へ移行できる。
- ParserVersionを更新しても、既存payloadの読み出し互換性が失われない。
- ML用CSVへ展開した設問数・値・欠損理由が正本と一致する。

## SPEC-CHANGE-005 メールアドレス・パスワード認証

| 項目 | 内容 |
|---|---|
| 状態 | 提案・会社承認待ち。認証契約と合成UIだけ先行し、本番接続しない |
| 対象 | 仕様書6.1、6.2、9.1、9.2、Usersシート |
| 衝突 | 仕様書9.1の「メールOTP方式。パスワードを独自保管しない」を変更するため、承認なしに本番採用しない |
| ログインID | 正規化したメールアドレス |
| パスワード | 管理者が初期設定できるが、平文・暗号化した可逆値・ヒントをSheetへ保存しない |
| 保存値 | Algorithm、ランダムSalt、反復回数、Verifier、更新日時、初回変更フラグ、失敗回数、ロック期限だけを制限付きUsersシートへ保存する |
| 初期方式 | PBKDF2-HMAC-SHA256、600,000回、16-byte Salt、32-byte Verifier。GAS実測後に安全性と所要時間を再承認する |
| 設定経路 | 権限管理者専用の設定画面またはサイドバーで検証値を生成し、Sheetセルへパスワードを直接入力させない |
| ポリシー | 15〜128文字。初期パスワードは初回変更を必須とする |
| 失敗制御 | 5回失敗で15分ロックし、更新をLockServiceで直列化する。存在しないIDにも同等の導出処理を行う |
| 応答 | ID不存在、REVOKED、誤パスワード、ロック中を外部から区別できない共通エラーとする |
| 権限 | ログイン成功後も全APIでUsersのRoleとStatusを再確認し、INPUT登録のみ・ADMIN全データ閲覧を維持する |
| セッション | HttpOnly、Secure、SameSite=Strictの既存方針を維持する |
| 回復 | 初期版はAUTH_MANAGERによるresetとし、OTP_ONLYとPASSWORD_WITH_OTP_RECOVERYは将来拡張として契約上残す |
| 保存境界 | ブラウザ・Cloudflare・GASでは処理中メモリだけで扱い、ログ、Web Storage、CacheServiceへパスワードを残さない |

PBKDF2の実装可否だけで安全性は確定しない。本番導入前にCloudflareでKDF処理時間・同時loginを、GASで認証transaction・lock競合を測定し、会社の認証方針、退職者失効、初期passwordの安全な伝達、reset本人確認を承認する。

2026-09-29追記: 利用者承認により、初期版はPASSWORD_WITH_ADMIN_RESETとする。password KDFはGASだけで実行せず、Cloudflare Functionの処理中memoryで行う候補を採用した。work factorとprotocolは実測・security review後に固定し、会社承認までは本番接続しない。詳細は`ADR-0001-password-auth-and-gas-boundary.md`を参照する。

### 必須テスト

- Usersシートの列集合に平文・可逆パスワード列が存在しない。
- 同じパスワードでも異なるSaltから異なるVerifierが生成される。
- 誤パスワード、存在しないID、REVOKED、ロック中の公開応答が同じである。
- 5回失敗、15分ロック、成功時の失敗回数解除を同時実行下でも正しく処理する。
- パスワード、Verifier、Salt、Cookie、セッションIDをブラウザconsole、Cloudflare、GASログへ出さない。
- INPUTは登録以外、ADMINは全データ閲覧・分析、AUTH_MANAGERは認証情報管理だけを行える。
- RoleまたはStatus変更が既存セッションの次回API呼出しへ反映される。
- 初回変更が完了するまで通常機能へ進めない。
- レスポンス、ブラウザ履歴、Web Storage、Cacheへ資格情報が残らない。

## SPEC-CHANGE-006 複数模試に耐える分析指標と目的別導線

| 項目 | 内容 |
|---|---|
| 状態 | 利用者方針承認済み。合成デモへ反映、本番接続は会社承認待ち |
| 比較指標 | 単一のSubjectDefinitionIDとMetricDefinitionID、または帳票に印字された総合指標を明示選択する |
| 禁止 | 受験した非総合科目を任意合算した得点率を校舎・生徒比較へ使用しない |
| 模試識別 | 提供元、模試種別、形式、年度、回次、SchemaVersionを独立管理し、画面上部へ常時表示する |
| 異形式推移 | 共通テスト型と記述型を既定で別系列表示し、定義・母集団・配点が一致しない値を1本の線へ接続しない |
| 帳票能力 | SchemaVersionごとに教科、偏差値、順位、分野、設問、無回答、過去回、志望校の取得可否をCapabilityProfileで管理する |
| 欠損との区別 | 帳票非対応、未受験、非掲載、解析不能、小人数抑制を別状態で表示する |
| 生徒属性 | 文理・国公私区分は初期版で保持せず、受験科目や志望校から推定しない |
| Person照合 | system生成PersonIDを使い、自動候補を管理者が確定した場合だけ回次比較する |
| 志望校 | 第1志望だけに限定せず全取得順位を扱い、大学・学部・学科／方式・入試方式を階層正規化する |
| 要確認 | 管理者設定の条件フィルタとして表示し、該当を危険判定・原因・指導指示として扱わない |
| 導線 | 状況をつかむ、集団を比べる、生徒を探す、志望校を確かめる、の4分類とする |

### 受入条件

- 画面内に「全教科合算得点率」が存在しない。
- 比較結果へ模試種別、年度・回次、選択指標、対象校舎数を常時表示する。
- 第1～第3志望の判定構成と、全志望を含む志望先別集計を表示できる。
- 文理・国公私区分をPDFから生成・推定しない。
- CapabilityProfileで非対応の分析は空値表示ではなく機能非表示または理由付き非対応表示にする。
- 要確認条件は設定版と条件文を表示し、原因や指導内容を出力しない。
- 原表記だけが一致する志望先を自動統合しない。
